## Developer responsibilities
Claude and Codex are peer developers. Each plans bounded work, maintains claims/handoffs, resolves CI, and handles eligible merges. **Cross-review is targeted, not universal.** Neither requires routine manager ACK for an already authorized disjoint task or eligible low-risk PR.
- Codex normally leads engine/save/region/resource compatibility; Claude normally leads approved maps/content and genuine mGBA QA. These are defaults, not exclusive expertise.
- **Self-merge eligible, low risk:** the author may merge their own **non-draft** PR only when its changed paths are exclusively documentation, trackers, design proposals, or isolated test/QA tooling (no production code or maps, saves, IDs, protected files, CI/workflows), *all applicable checks pass*, and an evidence comment names the exact head SHA, file list and actual test results. Recheck current main and pin the merge to that reviewed head (`--match-head-commit` or equivalent GitHub API SHA). Never call the author's own evidence an independent peer review. A design-only self-merge does **not** approve construction.
- **Peer-review required:** any PR touching game/engine production source, saves or their formats, map/layout/tileset/event data, permanent identifiers, protected paths, or workflows/CI. The nonauthor Claude or Codex must inspect the exact final source/evidence and record a substantive independent review and limitations before an eligible normal merge. Shared GitHub login cannot enforce separate reviewer identity, so explicit reviewer attribution is essential. If unavailable, advance other work without bypassing this gate.
- A rotating integration steward may be claimed in #15 for a batch. The steward refreshes the queue, checks collisions, merges one eligible PR at a time and rechecks main. It may self-merge **only** PRs satisfying the low-risk rule above; stewardship is no bypass or creative authority. A manager can assist with exceptions but is not a routine bottleneck.
- Respect existing paused sessions and reserved work. GitHub comments do not launch agents or authorize paid execution.

## Claims and handoffs
Post one scoped claim in #15:
`CLAIM | developer | branch/PR | literal paths | intended outcome | evidence | dependencies`.
Check live PR file lists and existing claims first. File-disjoint approved work proceeds immediately. Serialize the actual collision, including generator inputs and outputs; preserve dirty worktrees and every contributor's commits. Release a claim after merge, explicit transfer or abandonment.
A protected-path change requires a genuine authorized `HANDOFF_APPROVED PR=#N PATHS=literal,comma-separated,paths` matching that PR. No globs or directory-only handoffs. Content/map approval must precede its handoff. Do not fabricate approvals; obey the existing checker and its trusted-author rules.
At a session end, push recoverable work and leave one PR HANDOFF with remote full SHA, files, changes, exact commands and PASS/FAIL/SKIP counts, source/ROM hashes, fixture use, remaining risk, next executable action, and `WAITING_ON / RESUME_WHEN` when blocked. Do not rewrite shared status docs for each test run.

## Risk and review gates
| Tier | Scope | Minimum gate |
| --- | --- | --- |
| R0 | Prose, tracker, documentation or design **proposal only** | **Self-merge allowed** after exact-head author evidence, applicable guards and relevant link/content checks. A proposed route is not approved for production merely because its design document merged. |
| R1 | Isolated test/QA tooling and test-only experiments, no production source or reserved path | **Self-merge allowed** after meaningful passing positive/negative tests with nonzero counts, exact-head evidence and all applicable checks. New code in production engine files is **not** R1, even if small. |
| R2 | Runtime/game fixes, maps, graphics/game-data integration, protected paths | **Independent peer review required**, correct exact-head CI/native and NORMAL/RELEASE evidence, save/resource checks and genuine emulator evidence for visible behavior. |
| R3 | Save schema/migration, permanent identifiers, protected policy/workflows/CI, release/security | **Independent peer review required** plus reserved owner decision where applicable; strong compatibility, negative and rollback proof. Existing protections continue to apply. |

Tier is about impact, not file extension: executable workflows are R3; a design proposal can be reviewed as a proposal without authorizing construction.

Before merging (whether self-merge or peer-merge): refresh both full head and base SHAs, inspect the final diff and collisions, ensure non-draft, verify required checks and every applicable test. Publish exact-head evidence and pin the merge to that head; do not merge if the commit moved unexpectedly. A new commit invalidates review of changed content. Choose newest applicable check per workflow/job; a superseded canceled run is not a current failure, but missing/pending/skipped required checks are not PASS. Where integration changes tested behavior, reconcile in the feature branch or verify a disposable combined tree and record exact revisions. Never rely only on a mergeable flag.
Use the normal PR path, preserving history. Never direct-push main, force-rewrite shared branches, bypass rules, disable guards, change failure baselines to hide failures, or merge known failures. Verify main after merge and stop the affected integration lane on a regression. Preserve the prior good commit and repair or revert through a reviewed PR.
After integration, release claims and update the queue at a real status/dependency change. Do not mark a whole feature accepted from a partial test.

## Owner-only decisions
The owner retains geography and reference deviations, route openings, plot/canon, dialogue direction, Gym/trainer rosters, encounters/legendary placement, level curves/caps, art/music rights and personal likenesses, permanent map/section/heal/flag identities, origin encoding precision/migration policy, default cry-profile adoption and final release/Delta acceptance.
Developers present a bounded recommendation with alternatives and implications. They may autonomously implement already approved details, safe generic repairs, tests and tooling; approval of one map is not approval of every route.
Current decisions awaiting the owner are listed once in the [queue](INTEGRATION_QUEUE.md). Routine review, CI repair, claim arbitration and merge eligibility belong to developers.
